附项目源码！餐饮云平台的权限与多租户设计
餐饮云平台的多租户设计，难点不在“把租户 ID 加进表”，而在餐饮业务天然的多层级结构：集团、品牌、区域、门店、加盟商，数据既要隔离又要共享。权限设计也不能只做菜单按钮控制，而要落到数据行、操作动作和业务场景。本文聚焦设计思路，不贴代码，源码可在项目仓库中按模块对照。

一、先定租户模型。 餐饮 SaaS 常见三种租户：集团租户、单店租户、加盟租户。建议以“经营主体”为租户边界，集团下挂品牌和门店，门店作为数据归属单元而非独立租户。租户 ID 必须贯穿所有业务表，包括订单、菜单、库存、会员、支付、员工和日志。共享数据库共享 Schema 是成本最低的方案，但必须配合强制租户过滤、行级隔离和唯一索引设计；对合规要求高的客户，可预留独立库或独立 Schema 的升级路径。

二、权限模型分三层。 第一层是功能权限：角色能访问哪些模块和操作，如收银、退单、改价、盘点、导出。第二层是数据权限：能看哪个租户、品牌、区域、门店的数据，常见规则包括本人、本店、本区域、本品牌、本租户、跨租户运营。第三层是字段权限：手机号、成本价、毛利、支付流水等敏感字段是否可见、是否脱敏。三层要同时校验，只做功能权限会留下水平越权风险。

三、角色要贴近餐饮岗位，但避免硬编码。 老板、店长、收银、后厨、库管、财务、配送、运营的角色职责不同，且同一人在多门店可能有不同角色。建议采用 RBAC 为基础，叠加门店范围和条件规则：角色绑定权限点，用户绑定角色加数据范围。权限点用“资源:动作”表达，如订单:退款、库存:调整。高危动作单独授权，并要求二次确认或审批。不要为每个客户复制一套角色，应提供系统角色加租户自定义角色。

四、租户上下文必须可信。 租户 ID 不能由前端随意传入。登录后由服务端签发租户上下文，网关或拦截器统一注入，业务层从可信上下文取租户，而不是从请求参数取。所有查询、更新、删除必须带租户条件，数据库层可用行级安全或统一数据访问层兜底。跨租户运营后台要单独授权，操作留痕，禁止普通租户角色进入。

五、隔离要覆盖缓存、消息和文件。 多租户不只隔离数据库。缓存键要带租户前缀，消息主题或标签要带租户标识，文件存储路径按租户分区，搜索索引按租户过滤。异步任务和报表任务要携带租户上下文，避免消费者串数据。导出和打印同样要校验数据范围，防止通过报表绕过权限。

六、共享与隔离的平衡。 会员、菜品、供应商等主数据可在集团内共享，订单、库存、支付流水必须按门店隔离。共享数据要有授权关系：哪些门店可引用、哪些只能只读、哪些可本地覆盖。跨店调拨、集团报表、统一营销需要跨门店读取，应通过专门的服务和权限规则实现，而不是放开所有查询。

七、审计与租户生命周期。 记录谁在哪个租户、哪个门店、执行了什么动作、影响了哪些数据。租户开通、试用、续费、停用、数据导出和删除要有流程。停用后禁止登录但保留数据，删除要可追溯并满足合规。计费指标按租户和门店统计，避免资源被跨租户占用。

八、落地建议。 先做统一租户上下文和强制过滤，再做角色与数据范围，最后补字段权限和审计。用越权测试用例覆盖水平、垂直和跨租户场景。多租户设计的目标不是“隔离到最细”，而是让该隔离的绝不串，该共享的可控共享。权限与租户上下文成为基础设施，餐饮云平台才能既支持连锁扩张，又守住数据边界。
